# SAP-CUA implementation audit and first repair

**Audit date:** 7 October 2026  
**Repository:** `/Users/it-stock/Desktop/SAP_Computer_USE`  
**Target:** an OpenCUA-7B-based SAP Integration Suite agent, initially focused on Cloud Integration, with semantic actions, hybrid execution, independently verified outcomes, and a reproducible training/data pipeline.

## Assessment

The incoming implementation is a useful prototype with substantial scaffolding. It is **not yet a working SAP computer-use model or an end-to-end SAP automation product**. Several apparently complete paths simulate results, return success without executing actions, or write placeholder artifacts. Preserve the domain definitions, mock environment, data types, verifier functions, recorder event structures, and useful utility modules. Build connected vertical workflows on that foundation.

The baseline test run on Python 3.12.14 produced **265 passed and 17 errors**. After the first repair, **315 tests passed**. These are local software tests; they establish neither live SAP capability nor model quality. The inspected `datasets/` directory contains no data files, `model_registry/` contains only its README, and `apps/` contains no application files. No model training, real SAP operation, GPU job, or competitor evaluation was performed.

The Desktop repository already had tracked modifications and untracked source files. Those were included in the audit baseline. No Git reset, commit, branch replacement, or deletion of existing work is part of this repair.

## Highest-priority findings in the incoming code

1. **Task success was disconnected from task completion.** `agent/agent_loop.py` returned true unconditionally from its completion check, discarded model arguments, and passed an environment object into the router's boolean constructor argument. `api/routes/agent.py` and `evaluation/sapbench/runner.py` used confidence thresholds without executing actions. The router reported success when no executor existed. This made positive results unreliable.
2. **Named model adapters did not run the named models.** `model/__init__.py` returned a fixed center-screen click for OpenCUA and UI-TARS. The separate inference server has loading/generation code, but its generation paths use text inputs without the required screenshot/history processing. It is not connected to the agent adapter. Actual multimodal inference remains to be implemented and validated against upstream model documentation.
3. **Training is simulated.** `training/sft/__init__.py` creates mock model/PEFT objects and writes the strings `mock-lora-weights` and `mock-merged-weights` into files named as model artifacts. Its CUDA branch also invokes a mock training loop. QLoRA uses a mock quantization configuration. RL writes fixed synthetic metrics. A GPU alone will not make these paths perform training.
4. **Secret sanitization could leak or damage data.** Both trajectory processors applied text regex replacement to serialized JSON, then restored raw event data when parsing failed. Semantic-action metadata retained the raw event. Detection findings included secret substrings. Private-key redaction covered the header without reliably removing the body. Direct trajectory storage did not sanitize records.
5. **Benchmark definitions were not executable specifications.** Setup, verification, and cleanup placeholders were not expanded consistently with instructions. Setup and cleanup were unused. The runner did not execute actions or use the imported verifiers, and discarded its action trace in the final result. Many templates require verifier/setup types that do not exist.
6. **Deployment and message processing were conflated.** Mock deployment generated a successful MPL entry even without sending a message. The HTTP verifier returned success without observing an HTTP response.
7. **Service contracts were inconsistent.** Nine orchestrator tests errored because `db_path` was unsupported. Eight trajectory-store tests errored because `root_dir` and `db_path` were unsupported. Other latent mismatches included the runner payload, duration field, retry behavior, and a missing test import.
8. **Security and resource controls are not integrated.** Safety, prompt-injection, cost, audit, and telemetry modules exist as separate utilities. The central action loop did not enforce them. REST routes lack an integrated authentication/tenant-authorization layer, WebSocket authentication uses a hard-coded test key, and Groovy execution uses host subprocesses behind regex checks rather than OS isolation.
9. **The development instructions are not reproducible as written.** CI installs test tools without installing the project and its runtime dependencies. Packaging lacks an explicit build backend and CLI entry point. Make targets reference absent paths/modules. The API Dockerfile attempts installation before copying package source. Status documents disagree with the code and contain an obsolete instruction to remove `.git`.

## First repair implemented

The repair extends the existing code layout rather than replacing the repository:

- The agent preserves structured model arguments and GUI actions, records execution outcomes, and reports success only after a caller-supplied verifier confirms the task's state. A missing verifier leaves the task unverified.
- The API and benchmark share that execution loop. API tasks get unique IDs and bounded step counts. The benchmark applies supported setup, records trajectories, resets the disposable mock environment, and explicitly labels results as development-only mock runs.
- The router fails when no executor is connected; unsupported mock actions fail explicitly. Live adapters remain disconnected pending their integration and policy checks.
- Benchmark identifiers are expanded consistently across instruction/setup/verification/cleanup, with local seeded randomness.
- Mock deployment no longer invents a processed message. HTTP verification fails without an observed response. Tests that previously expected the HTTP stub to succeed were corrected.
- Structured sanitization runs recursively before JSON serialization, including nested semantic-action events, recorder files, and trajectory storage. Findings omit secret values; complete private-key blocks are removed. The duplicate processor delegates to the shared implementation.
- Action events are retained when screenshots repeat or are absent. Processor output names cannot escape the storage directory.
- Trajectories use independent UUIDs so multiple attempts do not overwrite each other, with persistent metadata indexing, filtering, export, and reopen tests.
- The orchestrator supports optional SQLite persistence, explicit runner success, duration tracking, and cancellation preservation. Retries require an explicit safe-to-retry decision. Its tests now use the documented Task callback, import TaskPriority, report explicit success, and opt into retries.

## Implementation sequence from here

1. **Reproducible development and explicit capability boundaries.** Fix packaging/CLI/CI/Compose; make simulation mode explicit for inference and training; prevent simulated artifacts entering the model registry. Gate: fresh installation and honest capability smoke tests.
2. **One complete SAP workflow.** Create package → create/import iFlow → deploy → send test payload → inspect correlated MPL → verify output → cleanup. Integrate the action policy, audit and budget controls, then attach verified API and browser adapters. Gate: the same task definition works in a deterministic local environment and, when access is available, a real SAP sandbox.
3. **Real OpenCUA inference and grounded actions.** Verify the exact upstream checkpoint interface, implement real multimodal processing, action parsing and coordinate conversion; compare a real untouched baseline against the deterministic executor baseline. Gate: reproducible screenshot-to-action and workflow results with model/checkpoint identity.
4. **Data collection and trustworthy evaluation.** Build capture, sanitization/review, provenance, versioned splits and resettable task fixtures. Expand only benchmark templates with working setup and independent verification. Gate: a versioned, non-overlapping train/validation/test release and replayable trajectories.
5. **Grounding and trajectory fine-tuning.** Implement real LoRA/QLoRA training, gradient checks, adapter load/reload and checkpoint lineage; add recovery training. Gate: measurable held-out improvement over the unchanged base model, with actual training cost and a GPU spend cap approved before running.
6. **Rollouts, later RL and product hardening.** Add controlled self-rollouts, verifier-derived rewards, evaluation-gated promotion, isolated code execution, authenticated tenant-aware console and operations. Gate: repeatable end-to-end performance, recovery and security evaluations. RL follows a trustworthy environment and SFT baseline.
